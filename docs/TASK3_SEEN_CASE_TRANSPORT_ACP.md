# ACP：Task3 已见案例模型传输韧性修复

- 状态：实验性提案，未进入正式 benchmark 架构
- 日期：2026-07-17
- 适用范围：Task3 企业面板已见案例工程回放

## 证据

一次性工程回放在 8/20 次 Provider Attempt 时终止。假设拆解与三套候选设计均已完成；其中一次 Schema 错误在同一逻辑调用的第二次尝试修复成功。必需的第一个 Reviewer 批次连续三次出现 `APIConnectionError / unknown_transport`，每次约 61–62 秒；第二个 Reviewer 批次随后在约 58 秒完成。统计执行、独立复算、Claim Gate 和 Manuscript IR 均尚未启动。

因此，本次直接原因是 Reviewer 长响应的传输失败，不是总预算耗尽，也不是人工 Gate 数量过多。H1–H4 是四个人工确认点；九次是一次完整工作流内部的逻辑模型调用数；二十次是包含修复与网络重试的 Provider Attempt 上限，三者不能互换。

## 决策

1. 保留四个人工 Gate、九个逻辑模型调用、每个逻辑调用最多三次以及全局二十次上限。
2. Qwen 的 JSON Mode 改用官方支持的流式输出，代码聚合完整 JSON 后再做 Pydantic 严格校验。
3. 仅对可重试传输错误、429 和 5xx，在同一逻辑调用内采用确定性的 2 秒、8 秒退避；Schema 修复不等待，也不增加 attempt。
4. Qwen 的两个 Reviewer 批次真正顺序执行；前一批终止失败时不再启动后一批。
5. 回执仅保存安全错误类别和哈希，不保存异常消息、URL、Prompt 或密钥；Recovery 映射不得丢失错误类别。
6. 不自动恢复证据不完整的跨进程或跨 Run 调用，不拼接不同轮次 Artifact。

## 不采用的方案

- 不提高二十次总上限或每逻辑三次上限来掩盖传输故障。
- 不删除 Reviewer、Probe 或任何证伪与审计步骤。
- 不把已见案例的后续工程回放重新命名为正式、隐藏或无偏 benchmark。
- 不因单次技术失败改写已经封存的 replacement-03 或本次一次性回放结果。

## 验收与晋级条件

代码变更先用 Mock/Fixture 覆盖流式聚合、用量统计、取消、退避、429/5xx、Schema 修复、错误类别和 Reviewer fail-fast，再通过完整后端、前端、构建与 diff 检查。

新的真实调用必须使用新的、明确授权的已见案例工程回放协议。即使硬指标通过，也只能说明同一已见案例上的运行可靠性；新的正式比较结论仍需未见留出案例的一次性评测。
